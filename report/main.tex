\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
EduFlex is a native Android learning platform that connects course discovery,
enrolment, lesson study, assessment feedback, and visible progress. XP, streaks,
quests, badges, and a leaderboard support continued interaction, while an
administration area manages users and learning content. The project investigates
how a mobile learning journey can be supported by consistent backend state and
observable operations.

The Java/XML client uses Material components and Retrofit to communicate with a
Spring Boot API. PostgreSQL is authoritative; Flyway versions the schema and jOOQ
expresses explicit SQL. Redis caches reads and tracks refresh sessions. RabbitMQ
defers content embedding, with local MiniLM vectors stored through pgvector.
Optional Gemini generation uses retrieved course material. Docker Compose supplies
the local topology, GitHub Actions automates verification, and Prometheus with
Grafana and Alertmanager exposes operational signals.

The principal engineering result is tested protection of learning transitions under
retry and concurrency. Transactions, learner row locks, conditional writes, and
unique constraints coordinate progress and protected rewards. On
\verificationdate{}, all \backendtests{} backend tests passed, including
\integrationtests{} PostgreSQL integration scenarios and a clean application of
\migrationcount{} migrations. One hundred simultaneous duplicate lesson-completion
calls left one progress row and one 20-XP reward. Earlier Android, live HTTP, release
build, and monitoring records are distinguished from this fresh backend run.

The report traces these results through architecture, data models, API contracts,
worked progression examples, failure analysis, and operational recovery design.
Source review also identifies incomplete assessment validation, unequal quiz
workflows, client-reported quest activity, order-sensitive course reward eligibility,
and broker publication gaps. These boundaries qualify the tested consistency
claims. Learning effectiveness, usability, sustained performance, and production
recoverability require further experiments; this report does not infer those outcomes
from the technology stack alone.

\noindent\textbf{Keywords:} mobile learning, Android, Spring Boot, PostgreSQL,
concurrency, semantic retrieval, messaging, observability.

\chapter{Introduction}
\section{Background}
Mobile devices make learning material available beyond the classroom, but
availability alone does not guarantee effective study. Learners also need a clear
path through content, immediate feedback, visible progress, and reasons to return.
Mobile learning systems therefore combine content delivery with interaction,
assessment, reminders, and progress tracking. Android was selected because it
supports a broad range of devices and mature libraries for navigation, background
work, networking, and accessibility \cite{androidguide}. A meta-analysis of 110
experimental and quasi-experimental studies reported a moderate average effect for
mobile-integrated learning, while showing that outcomes depend on instructional design
and context \cite{sung2016}. EduFlex therefore treats the phone as a delivery and
interaction channel rather than evidence of educational effectiveness by itself.

EduFlex connects these learner needs to a backend designed for data correctness and
operational visibility. The project is also an engineering portfolio: it demonstrates
an end-to-end system rather than an isolated interface or collection of endpoints.

\section{Problem statement}
Many prototype learning applications focus on screen design but do not address
problems that appear when an action is retried, several requests arrive together,
cached data becomes stale, or a dependency fails. One lesson completion can affect
progress, XP, quests, course completion, and badges. If these changes are independent,
a duplicated request may award a reward twice or leave partially updated data.

The project addresses two connected problems: providing a usable mobile experience
for discovering and completing learning content, and preserving trustworthy learning
state while supporting caching, asynchronous work, AI assistance, automated testing,
and monitoring.

\section{Research and evaluation questions}
The implementation is evaluated through four bounded questions:
\begin{enumerate}[leftmargin=*]
\item Can a learner complete the principal account-to-course journey through the
Android client and REST API?
\item Do duplicate and concurrent learning commands preserve one authoritative
progress transition and one protected reward?
\item Can asynchronous embedding and cache acceleration remain outside the
authoritative transaction while failures stay observable?
\item Can a developer reproduce the main build, integration, and monitoring checks
from versioned commands and infrastructure definitions?
\end{enumerate}
The report answers these questions with repository inspection and recorded verification.
It does not claim that EduFlex improves grades, motivation, or retention because no
controlled learner study was conducted.

\section{Objectives}
The main objective is to implement a functional Android learning application backed
by a secure and observable service. The specific objectives are:
\begin{itemize}[leftmargin=*]
\item provide account, course, lesson, quiz, review, payment-record, and gamification flows;
\item present consistent screens with loading, empty, validation, and failure states;
\item expose a documented REST API with authentication and role-based access;
\item store learning state in a versioned relational schema;
\item make progress and rewards safe under retry and concurrency;
\item move repeated reads and embedding work into bounded cache and background paths;
\item ground optional AI output in stored course material;
\item automate build and integration verification; and
\item expose application and infrastructure health through dashboards and alerts.
\end{itemize}

\section{Scope and limitations}
The scope includes a native Android learner application, an Android administration
area, Spring Boot, PostgreSQL/pgvector, Redis, RabbitMQ, Docker Compose, tests,
GitHub Actions, and a local monitoring stack. Firebase push, Supabase media storage,
and Gemini generation are optional integrations. The core development build works
without their credentials.

The checkout screen records development payment simulations and does not settle
real payments. Recovery requires configured SMTP; without it the application reports
that recovery is unavailable. The project does not publish a signed application to
Google Play. CI release outputs
are unsigned inspection artifacts. Centralized logs, distributed tracing, external
alert delivery, and automated database backup are outside the current deployment.

\section{Report organization}
The report moves from requirements and relevant research to implementation and
evaluation. It first explains the technology and architectural decisions, then follows
data, mobile, API, reliability, AI, and operational concerns. The final chapters map
claims to recorded evidence, state evaluation limits, and identify future work.

The report uses three distinct evidence levels. \emph{Implemented} means that a
behavior is present in the inspected source. \emph{Verified} means that a named test
or recorded experiment exercised it; the evaluation chapter states the date and
scope. \emph{Proposed} means that a design, acceptance criterion, or experiment is
future work. This distinction applies to diagrams as well as prose. In particular,
an acceptance-state diagram or recovery plan must not be read as a completed device
test or an executed disaster-recovery drill.

\chapter{Related Work and Design Position}
\section{Mobile learning}
Sung, Chang, and Liu synthesized 110 studies and found a moderate overall effect for
integrating mobile devices into teaching and learning \cite{sung2016}. Their analysis
also identified variation across instructional methods, intervention duration, and
implementation settings. This result supports mobile access as a useful design
opportunity, but it does not justify assuming that any mobile application improves
learning. EduFlex consequently focuses on observable interaction qualities---clear
progress, feedback, retry behavior, and access to ordered material---while reserving
pedagogical effectiveness for a later learner study.

\section{Gamification}
Hamari, Koivisto, and Sarsa found positive effects in many reviewed empirical studies,
while emphasizing that outcomes depended on the users and setting
\cite{hamari2014}. EduFlex uses XP, levels, streaks, quests, badges, and a leaderboard
to make activity and progress visible. Their presence does not establish improved
motivation. The current tests evaluate reward transitions. A learner study would
also need to examine continued use, perceived usefulness, and competitive pressure.

\section{Retrieval-grounded assistance}
Retrieval-augmented generation combines a generator with an explicit retrievable
knowledge source, improving provenance and allowing knowledge to be updated outside
model parameters \cite{lewis2020}. EduFlex applies the same broad pattern at project
scale: it restricts retrieval to one course, ranks lesson material through pgvector,
and returns source lessons with the answer. This is an engineering safeguard rather
than proof of factual correctness. Retrieval relevance and answer groundedness require
a labelled evaluation set that the present project does not yet contain.

\section{Project contribution}
EduFlex's contribution is the integration of a native learning client with a backend
that treats progress integrity as a first-class requirement. Its strongest evaluated
contribution is the transaction boundary joining lesson progress, course completion,
XP, quests, and badges under duplicate and concurrent requests. Caching, asynchronous
embedding, and monitoring are arranged around that boundary so operational features do
not become the source of truth. The project is a full-stack engineering case study,
not a controlled study of educational outcomes.

\section{Comparison with established platforms}
Google Classroom's mobile application centres on joining classes, assignments,
submission, communication, and limited offline access \cite{googleclassroommobile}.
Moodle exposes a much broader learning-management feature set through its web and
mobile clients, including course lists, activities, badges, and offline content, with
some capabilities differing between clients \cite{moodlemobilefeatures}. EduFlex is
not evaluated as a replacement for either platform. Its narrower contribution is an
inspectable reference implementation in which retry-safe progress and reward updates,
local semantic retrieval, and operational telemetry are evaluated together. It lacks
the mature collaboration, institutional administration, plugin ecosystem, and offline
learning support of established systems.

\section{Requirement prioritization}
Account security, course access, progress integrity, and build reproducibility are
mandatory because other features depend on them. Caching, message processing, and
monitoring improve performance and operations once the authoritative learning path
is correct. Optional external integrations add value but must not prevent a clean
developer build.

This priority influenced implementation order. PostgreSQL transactions and ownership
checks guard the core path. Redis and RabbitMQ surround that path without becoming
the authority for progress. Gemini, Firebase, and Supabase are configured at the edge
and can be absent in local or CI environments.

\chapter{System Architecture and Design}
\section{Architectural argument}
EduFlex is a modular application deployed as one Spring Boot process, accompanied by
specialized data and infrastructure services. It is not a collection of independently
deployable business microservices. Course, assessment, enrolment, and reward modules
share one relational database and can participate in the same transaction. This is
useful at the current scale because completing a lesson must update several related
facts without introducing a distributed commit protocol.

The design separates the \emph{authoritative path} from the \emph{derived path}.
Authenticated learning commands reach transactional services and PostgreSQL. Catalogue
caches and embedding vectors are derived representations: their absence or temporary
staleness must not authorize a learner or mint a reward. The monitoring path observes
both without becoming a dependency of each application request.

\responsibilitydiagram

This separation also defines what a future deployment can scale. Additional API
instances could share PostgreSQL and Redis because critical serialization occurs in
the database rather than a Java monitor. Embedding consumers could be separated from
HTTP serving to isolate CPU-heavy inference. Neither topology has been load-tested
here, so those are architectural extension points rather than demonstrated capacity.

\section{Overview}
The Android app sends JSON over HTTP and attaches an access token to authenticated
calls. The backend owns authorization, domain rules, storage, caching, messaging,
AI orchestration, and metrics.

\section{Backend structure}
Controllers define transport contracts and delegate to services. DTOs isolate wire
payloads from database records. Use-case classes perform validation and coordinate
repositories. Repositories contain JPA and jOOQ operations. Configuration supplies
security, caches, messaging, clocks, and metrics. This structure keeps business
invariants out of the mobile client and HTTP layer.

Figure~\ref{fig:backend-layers} makes the dependency direction explicit. Controllers
call application services, and services use repositories or integration clients.
Persistence code does not select HTTP responses, while Android does not calculate
authoritative rewards. These boundaries allow direct service testing and reduce the
effect of transport or database implementation changes.

\section{Deployment}
The base Compose stack runs the API, PostgreSQL/pgvector, Redis, and RabbitMQ.
Named volumes preserve database and cache state through ordinary restarts. Health
checks order startup by dependency readiness. The monitoring overlay adds Prometheus,
Grafana, Alertmanager, Blackbox Exporter, PostgreSQL Exporter, and Redis Exporter.

Only selected interfaces are published to the host. PostgreSQL, Redis, exporters,
and the Actuator management listener remain on the Compose network. This reduces
accidental exposure while retaining local access to the API, RabbitMQ management,
and loopback monitoring tools. Figure~\ref{fig:deployment} shows the topology.

\deploymentdiagram

The embedding listener currently runs in the same application process as the HTTP
API. The separate consumer node in the runtime figure is a logical responsibility,
not an independently deployed worker container. In addition, the base Compose file
persists PostgreSQL and Redis but does not mount a RabbitMQ data volume. A durable
queue declaration consequently must not be interpreted as durable broker storage
across container replacement.

These decisions favour a small number of clear failure boundaries. A later change
should be justified by a measured bottleneck or product requirement, rather than by
adding infrastructure solely to make the architecture appear more complex.

\section{Request and failure boundaries}
A mobile operation crosses the device-to-API boundary, the security-to-application
boundary, and usually an application-to-dependency boundary. Each can fail in a
different way. Connectivity failures produce a retryable mobile state. Authentication
and authorization failures return 401 or 403. Invalid input returns a validation
response. Transaction failures roll back related writes before an error leaves the
server.

This classification prevents an empty result from being confused with an error. An
empty catalogue is a successful query with no matching courses. A timeout, rejected
token, or unavailable database needs a distinct user message and operational signal.

\section{Aggregate boundaries and relational cardinality}
The schema distinguishes definitions from learner activity. A course and its lessons
describe reusable content. An enrolment connects one learner to one course. Progress
connects one learner to one lesson. Quiz attempts retain a history of submissions,
whereas a badge award represents a singular earned relationship. Combining these
concepts into one table would blur the difference between history and current state.

\learningerdetaildiagram

The detailed model in Figure~\ref{fig:learning-er-detail} makes the natural keys
explicit. Multiple learners can use the same lesson and a learner can study many
lessons, so progress resolves a many-to-many relationship. The unique user--lesson
pair prevents two completion records even when callers race. Attempts intentionally
have a different cardinality: a learner may submit an assessment several times.
This is why single XP does not imply a single attempt row.

Identity also comes from two different places. UUID primary keys identify resources,
while the verified JWT subject identifies the caller. Supplying a valid resource UUID
does not prove that the caller owns the associated learner record. Referential
integrity and authorization therefore solve complementary problems.

\section{Ownership and lifecycle}
The user row is the root for authentication and learner-specific records. Removing a
user cascades through progress and quiz activity where migrations explicitly define
that behavior. A course owns its lesson hierarchy, and a lesson may reference a
parent lesson for grouped content. Questions belong to lessons and options belong to
questions. This ordering lets content deletion remove dependent assessment data in a
predictable direction.

Enrolment is the bridge between catalogue data and learner activity. The backend
checks it before accepting learning mutations. Progress records answer whether a
specific lesson transition happened; the enrolment holds the broader course state.
Gamification statistics aggregate learner rewards, while attempts retain assessment
history. Keeping these concepts separate allows an attempt to be audited without
recalculating an already awarded first-pass reward.

\subsection{Assessment definitions and activity records}
A lesson may contain several questions, and each question may contain several
answer options. Correctness is stored on the option; the learner-facing
\texttt{GetQuizResponse} returns option identifiers and text without the correctness
flag. The question's \texttt{points} field is returned to the client, but the current
multiple-choice grader counts correct submitted items equally. Consequently, stored
points are content metadata rather than an implemented weighted scoring rule.

\assessmentmodeldiagram

Figure~\ref{fig:assessment-model} separates the answer key from attempt history.
The attempt table stores the learner, lesson, percentage, pass flag, and timestamp.
It does not persist each submitted answer or a version of the question set. A later
edit can therefore change the assessment without preserving the exact historical
answer key that produced a previous score. A durable assessment audit would need
versioned definitions and attempt-answer rows, rather than relying on the current
question options to reconstruct an old submission.

The hierarchy is also consequential: a quiz child points to its content parent
through \path{parent_lesson_id}. The foreign key confirms that the parent exists,
but does not itself require the parent to be in the same course or prevent a cycle.
Those rules would need additional validation. The diagram represents existing
relationships; it does not imply those missing constraints have been implemented.

\subsection{Reward definitions and daily state}
Gamification uses a statistics row for current totals and separate definitions for
badges and quests. The seeded quests are \texttt{QUIZ\_COUNT} (ten submissions,
100 XP), \texttt{STUDY\_TIME} (1,200 reported seconds, 80 XP), and
\texttt{PERFECT\_RUN} (three successive perfect submissions, 60 XP).
These values come from migration 1.2.3 and can change if the stored definitions are
edited. The daily progress key includes the configured local date, so the same quest
can be earned on another day without resetting yesterday's record.

\subsection{Deletion, retention, and reserved fields}
Deleting a course cascades to lessons and their progress and attempts through the
declared foreign keys. Reviews and transactions have separate foreign keys whose
original definitions do not specify the same cascade. Thus a generic course or user
delete can be blocked by dependent rows; the report must not promise universal
cleanup. The delete services do not implement a retention workflow or an archive of
historical achievements. Dynamic badge conditions encode a course UUID as text
rather than a course foreign key, so deleting a course also does not automatically
prove that its badge definition has been removed.

\section{Relational and vector data together}
Embedding columns live beside course and lesson records, so semantic retrieval can
apply normal relational filters before similarity ordering. A course question first
restricts candidate material to the requested course and only then ranks vector
distance. The benefit is one transaction and backup boundary for content and vectors.
The trade-off is that embedding dimensions and extension availability become part of
the PostgreSQL schema and migration process.

The current MiniLM model produces 384 values. A future model change with a different
dimension would require a planned migration and complete re-embedding. Recording the
model identity with future vectors would make mixed-model transitions safer.

\section{Queries, indexes, and connection budget}
The application uses a HikariCP pool with a default maximum of ten connections and
two minimum idle connections. Each active database transaction occupies a connection,
including time spent waiting for a learner row lock. Increasing the pool without
understanding query duration can move contention from the application to PostgreSQL.
The 32-connection integration-test setting is intentionally different and is not a
recommended runtime pool size.

Relational uniqueness supports enrolment and progress lookups. The semantic migration
adds IVFFlat cosine indexes with 50 lists to course and lesson embeddings. Such an
index is a search mechanism, not evidence that every query uses it or meets a latency
target. Query plans should be inspected on a representative dataset, and approximate
retrieval should be compared with an exact baseline before tuning lists or probes
\cite{pgvector}.

Migration \path{V1_2_7__secure_password_reset_and_payment_idempotency.sql} adds a
partial unique index for successful user--course transactions. Failed or non-success
history does not occupy that uniqueness boundary. Before applying the index, the
migration removes duplicate successful records; this is a data-changing upgrade and
would require backup and audit review in a deployment with real financial records.
The same migration adds hashed reset tokens with expiry and consumption timestamps.

\section{Networking and authentication}
The API URL is injected into \texttt{BuildConfig}; the emulator default is
\url{http://10.0.2.2:8080/}. Retrofit interfaces map each backend domain.
Debug builds enable HTTP logging and release builds disable it. After login, session
management stores the access token, refresh token, role, and profile information.
Provider secrets are never placed in Android build configuration.

The token manager gives networking code one location for bearer credentials. API
interfaces are divided by domain so course browsing does not depend on administrator
or payment details. Request and response models mirror the wire contract. This design
is intentionally pragmatic for the project scale: fragments coordinate their screen
state and adapters render collections, while authoritative rules remain on the server.

When a request fails, the screen retains enough context to retry without losing the
selected course. Authentication failures lead back to a valid session path; ordinary
network failures keep a retry action close to the failed content. Debug HTTP logging
supports development diagnosis, and disabling it in release avoids routine token and
payload exposure in release logs.

\subsection{Coordinating concurrent token refresh}
A mobile screen can issue several requests while its access token expires. If every
401 independently refreshes the session, the device creates unnecessary network calls
and races to update local credentials. \texttt{TokenRefreshCoordinator} synchronizes
the refresh decision. After entering the synchronized method, a caller compares the
token it sent with the token currently stored. If another request already installed a
replacement, the caller reuses that value; otherwise it performs the refresh.

\tokenrefreshdiagram

The OkHttp authenticator bounds the retry chain to avoid an infinite refresh loop.
The refresh request uses the unauthenticated Retrofit client so that it does not invoke
its own authenticator recursively. An I/O failure is distinguished from an invalid
refresh response: transient connectivity does not immediately erase the saved session.
The existing Android unit test exercises concurrent expired requests and verifies that
they share one refresh call. This is an in-process coordination property; it does not
claim synchronization across devices or processes.

\subsection{Transport budgets and device state}
The clients configure a ten-second connection timeout, thirty-second read and write
timeouts, and a forty-five-second total call budget. These values bound waiting on a
dependency; they do not define a measured user-facing performance objective. The
ten-megabyte OkHttp disk cache follows HTTP cache semantics and should not be confused
with a complete offline course store.

Local session data supplies navigation and bearer credentials, but the backend remains
the authority for enrolment and rewards. The optional \texttt{X-User-Id} request header
is not proof of identity: ownership checks use the authenticated principal. A production
mobile threat review should also examine credential storage, device compromise, and
TLS configuration rather than assuming that JWT usage secures every client boundary.

The inspected main manifest enables cleartext traffic and application backup; the
token manager persists session values in ordinary SharedPreferences. Those are
concrete development defaults, not an encrypted transport or credential-storage
guarantee. A production variant needs a deliberate HTTPS/network policy and a review
of backup and local session handling. Release HTTP logging being disabled addresses
one disclosure path while leaving these separate policies unresolved.

Study-time reporting also has a device lifecycle boundary. The lesson fragment
records elapsed foreground time between \texttt{onResume} and \texttt{onPause}, then
posts the measured seconds to the quest endpoint. The callback logs a network failure
but does not persist a retryable event. This measures foreground elapsed time rather
than attention, and it can lose a contribution when delivery fails. A future offline
outbox for study events would need server deduplication as well as persistent client
storage; replay without an event identifier could otherwise credit the same interval
twice.

The multiple-choice SQL joins the supplied option to its question and the selected
lesson, preventing a correct option from another lesson from being counted as a
correct response. This is useful scope protection, but the use case sets
\texttt{totalQuestions} to the size of the submitted list. It does not compare that
list with the authoritative complete question set or reject repeated question IDs.
For a four-question quiz, a submission containing one correct item is consequently
computed as $1/1 = 100\%$, rather than $1/4 = 25\%$. Repeating a correct question
can similarly distort the assessment and perfect-run count. These examples are
deduced from the inspected grading loop, not presented as new live HTTP test results.

Correct grading should first resolve the server-owned question set, require exactly
one allowed answer per required question, reject unknown and duplicated identifiers,
and then calculate the score against that set. Whether questions have equal weights
or use stored points should be an explicit contract. No concurrency mechanism can
repair a score computed from an invalid submission.

The fill-in-the-blank path has additional gaps. Its \texttt{lessonId} is not used

feedback is built. That is a server-error risk rather than a deliberate ``question
not found'' response. The request also lacks the equivalent bean-validation coverage.
These are reported implementation defects, not limitations inherent to text questions.
The next implementation should reuse the validated assessment scope and define
whether this mode is practice-only or earns the same persisted progression.

\section{Activity trust and overlapping contracts}
\label{sec:activity-trust}
An owner check establishes whose record a caller can change. It does not establish
that the caller studied, attempted a quiz, or measured time honestly. The daily quest
progress endpoint currently accepts a \texttt{questType} and arbitrary integer
\texttt{increment} from the authenticated owner. The service can award a quest when
the resulting count reaches its target. This preserves one completion reward per
day, but allows client-reported activity to qualify without server-observed evidence.
The explicit XP-grant route is administrator-only; the quest reporting route is a
separate trust boundary and must be evaluated independently.

A stronger policy would derive quiz and perfect-run contributions only from
validated, uniquely identified assessment submissions. Study-time credit needs a
defined evidence model, bounded intervals, and replay handling. Even a heartbeat
cannot prove learner attention, so the product should describe reported study time
honestly. Merely adding a maximum increment would restrict obvious abuse without
fully establishing activity authenticity.

There are also overlapping review contracts. POST \url{/api/course/reviews} checks
the request owner and enrolment. POST \url{/api/course/{courseId}/reviews} obtains
the user from the JWT and validates the course and review fields, but its use case
does not check enrolment. They share the review storage while applying different
eligibility rules. A canonical policy and route should be selected before claiming
that all course reviews are restricted to enrolled learners.

Authenticated catalogue access should not be confused with course entitlement.
GET \url{/api/lesson?courseID=...} and GET \url{/api/quiz/{lessonId}} have no
course-enrolment check in their inspected controller/use-case paths. AI assistance
does check enrolment, and progress mutations do check it. If paid courses are intended
to protect content delivery as well as learning mutations, these reads require the
same policy. The current development checkout is not a complete commercial access
control system.

\section{Authentication and authorization}
Passwords use BCrypt. Login returns a 15-minute access token with identity, email,
role, and token type, plus a 30-day refresh token with a unique identifier. Refresh
state is held in Redis and logout revokes it. Spring Security uses stateless sessions.
Public routes include registration, login, recovery, refresh, logout, health, and
API documentation. Other routes require authentication. Administrator operations
require the \texttt{ADMIN} role; learning mutations also validate ownership.

Figure~\ref{fig:auth-sequence} follows both the initial login and later refresh.
The access token is self-contained and short-lived. The refresh token is longer-lived,
but its identifier is checked in Redis, which gives logout a server-side revocation
point. A refresh token is not accepted as an access token because the signed token
also carries a token-type claim.

Logout deletes the selected refresh-token record. It prevents that refresh token from
minting another access token; it does not immediately invalidate an already issued
15-minute access token. This bounded residual session is a consequence of stateless
access-token validation.

\authsequencediagram

Authorization has two levels. Route rules decide whether a role may reach an endpoint.
Application rules then check whether the authenticated learner owns the requested
user path and is enrolled in the relevant course. Role checks alone cannot protect a
request such as ``save progress for user B'' made by authenticated user A.

\section{Single-use password recovery}
Account recovery is a separate credential lifecycle rather than a direct password
update keyed by an email address. When delivery is configured, the service generates
32 random bytes with \texttt{SecureRandom} and encodes them as a URL-safe token. Only
the SHA-256 digest is stored in PostgreSQL; possession of the stored digest alone does
not provide the code submitted by the learner. The default lifetime is fifteen minutes.

The request response uses the same message for an existing and an unknown account,
reducing direct account enumeration through response text. When no delivery bean is

and concurrent recovery requests have not been demonstrated end to end.

The transaction spans the PostgreSQL token and password changes, but it does not form
a distributed transaction with SMTP or Redis. For example, a delivered email can outlive
a database rollback, and Redis revocation cannot be undone by PostgreSQL. Rate limiting,
delivery retries, a session-version strategy, and explicit failure tests remain useful
next steps. Issued access tokens retain their normal expiry boundary.

The configured lifetimes are shorter for changing learner state and longer for badge

\subsection{Cache invalidation and consistency boundary}
The configured cache manager is transaction-aware, so transaction-bound cache changes
can be deferred until commit. This avoids evicting or publishing derived cache state
as though an authoritative write had succeeded when its database transaction later
rolls back. The embedding listener currently clears the entire semantic-search and
summary caches, rather than selecting only one changed course.

The inspected eviction lists are incomplete. Course listing is cached twice: an
outer \texttt{courses} response keyed by user and an inner \texttt{courseCatalog}
query keyed by administrator/active view. Course writes evict the inner catalogue,
summary, and search entries, but do not evict the outer \texttt{courses} response.
The client can consequently continue receiving an old outer result until its
five-minute TTL expires. Lesson creation clears summary and search caches but omits
the cached lesson list; lesson update and deletion do clear that list. This is a
specific missing-invalidation issue in addition to the generic concurrent-fill race.
Search also excludes already-enrolled courses, but successful enrolment does not
invalidate that learner's cached search results. A cached suggestion can remain
visible for up to its fifteen-minute lifetime after the learner joins the course.

A regression should warm the actual route, mutate the content, immediately reread
it, and verify the new version without waiting for expiry. Every outer and inner
representation must appear in a mutation-to-cache dependency map. Clearing a
different cache name is not sufficient simply because both caches describe courses.

Annotation-based caching also has an important implementation constraint: calls must
cross the Spring proxy for the annotations to apply \cite{springcache}. An annotation
on a self-invoked method is not evidence of a cache hit. Similarly, enabled cache
statistics describe instrumentation capability; a recorded hit ratio is needed before
claiming fewer database reads. Fallback summaries are explicitly excluded from caching
by the service's \texttt{unless} condition, and the course-question method itself is
not annotated as a cached answer operation.

TTL expiration bounds the lifetime of a stored copy, not every race. A reader that
loads old data just before a commit may repopulate a stale copy after eviction.
Versioned keys, coordinated cache loading, and a staleness test are possible future
controls. No cache-stampede prevention or general Redis fail-open policy is claimed.

\chapter{Reliability, Concurrency, and Messaging}
\section{Transactional updates}
Content completion coordinates progress, XP, streak, course state, and badge
evaluation. Multiple-choice submission additionally records assessment history and
updates daily quests within its transaction. Fill-in-the-blank feedback does not
currently execute those state changes. An injected failure after intermediate
writes verifies rollback for the tested transactional path, so a later retry can
complete its protected transitions once.

The rollback argument is scoped to transaction boundaries and exception behavior.
With Spring's default declarative rules, an unchecked exception reaching the
transaction interceptor triggers rollback \cite{springrollback}. Catching an
exception inside a transactional service and returning a failure DTO is not, by
itself, a rollback instruction. For example, the lesson-creation service catches a
broad exception while creating a main lesson, its quiz child, and content events.
That path needs a dedicated failure test or an explicit rollback policy before the
same all-or-nothing claim can be extended to every content command. The existing
injected rollback test establishes its own exercised learning path.

\subsection{Invariants rather than successful responses}
The design starts from final-state rules. A content lesson has at most one
user--lesson progress row. A successful first completion contributes 20 XP once.
A repeated completion preserves its timestamp. Course completion and badge awards
must not depend on whether the final content lesson or final quiz commits first.
These are database properties, not claims about how many HTTP responses return 200.

If two requests both read an incomplete state before either writes, an application-only
check can award XP twice. EduFlex therefore creates the statistics row with
\texttt{ON CONFLICT DO NOTHING}, locks it in the transaction, and uses affected-row
counts to decide whether each transition is new. PostgreSQL holds conflicting row
locks until transaction completion, which makes the serialized decision visible to
the next writer \cite{postgreslocks}.

\concurrenttransactiondiagram

Figure~\ref{fig:concurrent-transaction} follows the same learner through two calls.
The second waits for the first transaction, then observes completion and skips the
protected reward. If the first transaction fails, the second can instead become the
first committed completion. Calls for different learner rows do not acquire this
same logical lock.

\begin{lstlisting}[language=SQL,caption={Implemented per-learner lock initialization and acquisition}]
INSERT INTO gamification_stats (user_id, xp, level, streak_days)
SELECT user_id, 0, 1, 0 FROM users WHERE user_id = ?
ON CONFLICT (user_id) DO NOTHING;

SELECT * FROM gamification_stats
WHERE user_id = ?
FOR UPDATE;
\end{lstlisting}

The transaction updates XP arithmetically in SQL rather than performing a detached
read--modify--write in Java. Level is derived from the resulting XP with
$\lfloor XP/100 \rfloor + 1$. Conditional course completion determines the single
transaction allowed to award completion benefits. The test suite deliberately changes
the content/quiz ordering to verify this rule.

\section{Per-learner serialization}
The service locks the learner's statistics row with PostgreSQL
\texttt{SELECT FOR UPDATE}. Requests for one learner serialize at the critical
transition, while different learners proceed independently. Conditional updates
decide whether a transition is new and uniqueness constraints provide a final
safeguard. Protected transitions include lesson completion, daily check-in,
first quiz pass, course completion, quest completion, and badge award. Free-course
registration separately relies on its unique learner--course constraint rather than
this learner-lock workflow. Its pre-insert check can still race: one call succeeds
and another can receive a failure even though the single enrolment is preserved.

Figure~\ref{fig:progress-state} shows the lifecycle seen by repeated requests. A
duplicate does not reverse the learner or create a second protected reward; it returns
the state that already won the race. This property matters on mobile networks, where
the server may commit even when the client never receives the response.

\section{RabbitMQ embeddings}
Course and lesson services publish a content-change event after transaction commit.
A durable queue feeds a listener with prefetch 10 and three retry attempts. The
listener creates a MiniLM vector, stores it, and invalidates related caches.
Publication outcomes and processing duration are measured.

The configuration also declares a durable \path{gamification_queue} and its binding.
No corresponding gamification listener implements the reward workflow in this
snapshot. Rewards are computed synchronously inside PostgreSQL transactions. A
declared queue is therefore not evidence of asynchronous gamification processing.

Figure~\ref{fig:embedding-sequence} explains the ordering. Publishing before commit
could let the consumer read old content or embed a write that later rolls back.
After-commit publication avoids that ordering error and keeps model inference outside
the HTTP response time.

\embeddingsequencediagram

The design currently has no transactional outbox or publisher confirmation. A
committed content write can therefore exist without a durable event if publication
fails. Operators must react to the alert and replay affected content.

\subsection{Delivery semantics and stale vectors}
The event payload contains a content type and UUID, and is routed through the
\path{eduflex_exchange} direct exchange with \texttt{content.changed} to
\path{content_embeddings_queue}. The listener reloads current content instead of
trusting a full text snapshot carried by the message. Reprocessing can overwrite an
embedding without awarding a learner reward because the consumer owns derived vectors,
not gamification.

Broker durability, publisher confirmation, and consumer acknowledgement are distinct
boundaries \cite{rabbitconfirms}. Here, the \emph{sent} metric means that the RabbitTemplate
call returned; it is not a durable broker confirmation. Listener retries are bounded,
but there is no explicit dead-letter/reconciliation workflow. A transaction outbox
would close the database-commit-to-publication gap by committing the event record with
the content and delivering it later.

Reloading current text avoids embedding an obsolete message snapshot, but it is not
a full version-ordering protocol. With concurrent consumers, an older computation
could still finish after a newer one and overwrite its vector. The current listener
has no content-version comparison. Any future increase in worker concurrency should
include versioned writes and an out-of-order completion test.

\subsection{Calendar time and reward semantics}
Daily rewards use the configured calendar zone, defaulting to
\texttt{Asia/Ho\_Chi\_Minh}, rather than assuming every learner day ends at UTC midnight.
The update awards ten XP only when the stored date is absent or earlier than today's
date. Login and explicit check-in share this boundary. Fixed-clock tests cover same-day
retries, the next local day, and a future-dated record that must not move backward.
Time is therefore an explicit input to the rule rather than a dependence on when the
test happens to execute.

Daily check-in and study streak are separate fields and rules. The former records
\path{last_login_xp_date}; it does not itself advance \path{last_study_date}. Streak
updates set the count to one on first activity, preserve it on another activity on
the same date, add one when the last date is yesterday, and restart at one after a
gap. Unlike the check-in future-date guard, the streak method's remaining branch
also restarts a future-dated record. The report does not claim a shared future-date
policy for both operations.

\section{Worked progression examples}
\label{sec:progression-examples}
Let $T$ be the number of lessons in a course with no parent, and let $C$ be the number
of those lessons completed by the learner. The stored display percentage is
\[
 P = \begin{cases}
  0, & T=0,\\
  \operatorname{round}(100C/T,1), & T>0.
 \end{cases}
\]
Terminal course completion uses the integer condition $C=T$ with $T>0$, rather than
testing the rounded display value. This avoids treating a display rounded to 100 as
proof that every counted lesson is complete.

Consider a course with two top-level content lessons A and B, and one quiz child Q
under B. Here $T=2$, not three. Completing A creates its progress row, gives 20 XP,
and sets $P=50$. Passing Q for the first time gives 30 XP and completes both Q and
its parent B. The two top-level lessons are now complete, so the winning course
transition gives 50 additional XP and awards the course badge. Ignoring independent
daily and quest rewards, this ordering totals 100 XP. It does not grant the 20-XP
content reward for B because B was completed by the quiz workflow.

If B was explicitly completed before Q, its first content transition earns its own
20 XP. Course completion may therefore occur earlier according to the top-level
counting rule. This example shows why progress, assessment mastery, and reward
eligibility should be specified separately: the current state machine is not a rule
that every child quiz must be passed before a course can appear complete. Product
requirements should decide whether that policy is appropriate before changing the
denominator or introducing prerequisite enforcement.

\chapter{AI-Assisted Learning}
\section{Retrieval}
The local all-MiniLM-L6-v2 model produces 384-dimensional course and lesson vectors.
A learner question is embedded and compared with lesson vectors from the selected course
using pgvector. Constraining retrieval by course reduces unrelated context.

The embedding service uses LangChain4j's in-process ONNX model rather than an
external embedding API \cite{langchainonnx}. Its wrapper passes a text segment to
the model and serializes the returned floats for PostgreSQL. The upstream model card
describes an English sentence and short-paragraph encoder, with default truncation
beyond 256 word pieces \cite{minilmmodel}. That model-card default should not be
mistaken for a separately verified token limit of this Java wrapper. The deployed
library's tokenization and truncation need an explicit check before claiming that an
entire long lesson is represented by its single vector. Vietnamese or mixed-language
course retrieval also needs its own benchmark; local inference is not proof of
multilingual retrieval quality.

Embedding is a representation step rather than an answer-generation step. Vector
distance lets differently worded questions locate related lessons. The relational
course filter defines retrieval scope. The controller supplies the enrolment or
administrator check before retrieval; vector similarity supplies ranking rather than
authorization.

\subsection{Catalogue search and course question retrieval}
Catalogue search has a different ranking policy from course question retrieval.
The catalogue search service first requests up to ten keyword matches. If those
results do not fill the limit, it embeds the query and adds semantic course matches.
A LinkedHashMap preserves keyword-first order and removes duplicate course UUIDs.
The final list is capped at ten; it is not a single globally reranked blend of lexical
and vector scores. The cache key includes user identity because the query excludes
courses in which that learner is already enrolled.

Course questions instead rank lesson vectors within one enrolled course. This
separates discovery from grounded assistance: a good course-level title match does
not prove that a particular lesson contains an answer. Query embedding remains
synchronous in both search and question requests. RabbitMQ defers content-vector
refresh; it does not move every AI operation off the request thread. Background
inference also shares the API process's CPU and memory, so queuing does not create
independent compute capacity.

\subsection{Scoring and context construction}
The repository ranks lessons by pgvector cosine distance and returns relevance as
$1-d_{\mathrm{cosine}}$. This is a similarity score, not a probability that the answer
is correct. The query filters by course UUID, excludes null embeddings, and returns
at most five lessons. When no vector result exists, the service selects up to five
stored course lessons. That fallback is ordered by lesson UUID in the repository and
is not a learned relevance ranking.

\begin{lstlisting}[language=SQL,caption={Course-scoped retrieval implemented by the repository}]
SELECT lesson_id, title, content,
       (1 - (embedding <=> ?::vector))::float AS relevance
FROM lesson
WHERE course_id = ? AND embedding IS NOT NULL
ORDER BY embedding <=> ?::vector
LIMIT 5;
\end{lstlisting}

One vector is stored per lesson, not per independently indexed text chunk. Context
construction truncates each lesson excerpt to 1,500 characters and uses a 14,000-character
budget check for the excerpt accumulation. Metadata and headings mean this is not a
strict token cap. The generator requests temperature 0.2 and at most 700 output tokens.
These are code-level bounds; their adequacy for long lessons has not been measured.
Versioned chunking and a labelled retrieval benchmark are appropriate extensions.

A useful future retrieval record would contain the content version, embedding model
identifier, chunk boundaries, language, and generation timestamp. A model change
cannot safely be treated as a cache refresh when vectors produced by different
encoders share the same search space. The migration should regenerate a coherent
index and compare ranked results before switching readers to it. These metadata and
version-switching mechanisms are proposed; the current rows hold only the lesson or
course vector alongside their other content fields.

\section{Grounded generation and fallback}
Retrieved lesson excerpts become context for optional Gemini generation. The result contains
source information so the UI can identify supporting material. Expensive summaries
and search results are cached. Without \path{GEMINI_API_KEY}, summaries use a
deterministic overview and questions return retrieved lesson suggestions, allowing
local development and tests without provider access.

The inspected default model remains \texttt{gemini-2.0-flash}. Google's release
notes record that model's shutdown on 1 June 2026 \cite{geminireleases}. Consequently,
configuring only an API key is not evidence that the default live-generation path
works at this report's October snapshot. A supported model must be selected through
\path{GEMINI_MODEL} and verified against the integration's request/response contract.
No credentialed provider check was performed during this report revision. Existing
fallback behavior is useful degradation, but it does not repair an obsolete model
configuration or establish generated-answer quality.

The backend returns sources with the answer instead of presenting generated prose
alone. This gives the learner a route back to the lesson and lets an evaluator inspect
retrieval quality. If retrieval selects weak evidence, fluent wording does not make
the evidence stronger; source visibility makes the weakness observable.

\section{Responsible boundaries}
Prompts, learner IDs, emails, tokens, and questions are excluded from metric labels.
Answers remain attributable to stored course content and are not treated as
authoritative academic assessment. Provider outcomes use bounded metric labels.

Course text is embedded locally, but retrieved excerpts and the learner's question
are sent to Gemini when generation is enabled. Local embeddings therefore do not mean
that the entire AI path remains on the host. An instructor-uploaded excerpt is also
untrusted prompt input: an instruction in course material should not override application
policy. Source attribution and a low generation temperature are useful presentation
choices, but they are not prompt-injection controls or guarantees against hallucination.

\section{Quality evaluation approach}
The current automated test proves deterministic fallback behavior. A broader AI
evaluation should prepare representative questions for each course, expected lesson
sources, and educator-reviewed answer criteria. Retrieval can then be measured through
source recall and ranking, while generated responses can be judged for groundedness,
completeness, and unsupported claims. Latency and provider failure rate should be
reported separately from content quality.

This evaluation remains future work because the repository does not contain a labelled
educational benchmark. The report describes the implemented retrieval pipeline without
claiming a measured pedagogical quality threshold.

\section{Operational security}
\subsection{What custom metrics do and do not establish}
Progress and reward counters register their increments after transaction commit, so
an injected rollback does not appear as a committed reward. They remain operational
counters: process restarts reset them, and they are not a durable accounting ledger.
The statistics acquisition timer wraps both row initialization and the locking query;
it includes database round-trip work and is not an isolated measurement of lock wait.
Correlating it with Hikari pending connections and PostgreSQL activity is therefore
more useful than assigning every increase to one cause.

AI counters distinguish provider output from fallback by mode. The fallback label
includes both absent configuration and provider failure, so it cannot by itself
establish a provider-error rate. Similarly, an embedding processing success measures
the listener operation, not necessarily the relevance of the stored vector. These
definitions prevent visually impressive dashboards from overstating evidence.

\subsection{Exposure and access}
Liveness and readiness are exposed on the main API port. The monitoring profile
exposes only health and Prometheus on internal port 8081. Grafana, Prometheus, and
Alertmanager bind to loopback locally. The PostgreSQL exporter uses a dedicated
\texttt{eduflex\_monitor} role with \texttt{pg\_monitor}. Prometheus retention is
bounded to seven days or 2 GB.

The current Alertmanager receiver groups alerts for inspection in its local web UI but
does not send email, chat, or paging notifications. External delivery is therefore a
future deployment task rather than an implemented operational guarantee.

\section{Operational interpretation}
The dashboards correspond to questions asked during an incident. Service Overview
shows whether the API is unreachable, slow, failing, or waiting for database
connections. Dependencies narrows pressure to PostgreSQL, Redis, or RabbitMQ.
Learning Operations shows progress transitions, rewards, row-lock time, embedding
work, and AI outcomes.

An alert starts an investigation; it does not prove one cause. High latency together
with Hikari pending requests points toward database work or pool saturation. A growing
embedding queue with zero consumers points toward listener startup or broker
connectivity. Redis eviction requires inspecting memory policy and workload before
capacity changes. The monitoring runbook records these decision paths and recovery
checks.

An availability signal describes an observed condition; an alert threshold describes
the operator's configured decision policy. The current one-second latency threshold
is not a measured service-level objective. Request-volume guards reduce noisy ratio
alerts during very light traffic, which is particularly relevant to a local student
project.

\subsection{Operational maturity and deployment limits}
The local topology has one database instance, one broker, and one API process. It does
not provide automatic failover, database point-in-time recovery, an ingress TLS layer,
or a rolling-deployment controller. Redis AOF and named database volumes preserve local
state through ordinary restarts, but they are not backups. An operator must separately
test restoration from an independent copy.

Refresh-token revocation currently finds a user's Redis keys by pattern. This is simple
for a small environment but should be replaced by a bounded scan or indexed session set
before a large keyspace is supported. Separating session state from disposable caches
would also make eviction policy easier to reason about. These limits explain why passing
the monitoring smoke test does not establish production readiness.

\section{Recovery design and state classification}
\label{sec:recovery-design}
Recoverability depends on which state was lost. PostgreSQL holds identities,
enrolments, attempts, progress, and reward totals. Redis holds both disposable read
caches and security-relevant refresh-token records. RabbitMQ carries unfinished
embedding work; a vector can be regenerated from current content, but a missing
reward history cannot be reconstructed from a cache. This classification determines
the recovery order instead of treating every container as interchangeable.

\restoreplandiagram

Figure~\ref{fig:restore-plan} is a proposed exercise, not evidence of an executed
recovery. A suitable first step is a PostgreSQL logical backup restored into an
isolated compatible database. PostgreSQL documents the snapshot consistency of
\texttt{pg\_dump}, custom-format restoration with \texttt{pg\_restore}, and the
separate handling of cluster roles \cite{postgresbackup}. The project does not yet
automate these procedures. A continuous WAL archive and base backup would be a
different recovery design; the current Compose volume does not supply it.

The drill should state the latest recoverable data boundary and elapsed time until
verified service restoration, rather than inventing a recovery-time target. It should
compare representative user, enrolment, progress, attempt, and XP records before and
after restoration. It should also test whether stale caches or still-issued tokens
can expose a database state that has moved backward. Resetting a container without
restoring an independent copy is a restart test, not a backup-restoration test.

\subsection{Reproducibility and deployment drift}
The Compose files pin several monitoring images to explicit versions, while
\path{pgvector/pgvector:pg16}, \path{redis:alpine}, and
\path{rabbitmq:3-management-alpine} are floating tags. They identify a product or
release family rather than immutable image bytes. An environment manifest should
record resolved digests, JDK, schema version, active profile, dependency versions,
and non-secret configuration alongside the source revision. Wrappers and Flyway
improve repeatability, but they do not make mutable image tags or an uncommitted
working tree immutable.

Before a deployment, migrations should be rehearsed on a representative restored
dataset, health checks should pass on both the application and management listeners,
and the client contract should be checked against the active API. Adding API replicas
would introduce additional cache and embedding races rather than automatically
proving horizontal scalability. The report's single-host topology is the inspected
implementation; a multi-host deployment requires its own design and evidence.

\subsection{Threats to validity}
The clean Testcontainers database controls schema setup and makes transaction tests

traffic. The concurrency harness synchronizes service callers and verifies final state;

The historical emulator evidence covers one API level and representative navigation.

validate deterministic behavior rather than educator-approved answers. These are limits
of coverage and experimental design, rather than reasons to discard the verified

\subsection{A repeatable measurement protocol}
The following protocol is proposed, not a completed benchmark. First, seed a fixed
dataset with documented numbers of users, courses, lessons, enrolments, and vectors.
Keep the same data, API profile, database pool, image digests, machine resources,
and test script for each comparison. Disable external generation for core API
measurements and evaluate provider-backed requests separately, so remote provider
variation is not mistaken for database or cache behavior.

Measure catalogue reads, progress mutations, and course questions as separate
workloads. For cache experiments, use cold, warm, and post-mutation phases. Confirm
the expected cache outcome and returned content in each phase; warm reads with stale
data are not a successful optimization. For concurrency, compare many callers for
one learner with the same request count spread across distinct learners. These
exercise deliberate per-learner serialization and shared resource saturation
respectively. Include new completions and retries separately because their database
work and reward outcomes differ.

Record the offered request rate, completed throughput, client-observed latency,
timeouts, HTTP outcomes, and correctness assertions. Report percentiles per route
rather than only a pooled average. Count timed-out and failed requests in the
experiment outcome instead of silently excluding them. Repeat steady-state runs,
publish the raw records, and preserve the warm-up and measurement windows in the
script. A closed-loop caller count must be described as such; it does not represent
an independently scheduled arrival rate.

For embeddings, record both content commit time and the time the matching current
vector becomes available. Consumer execution duration alone excludes time waiting
in the queue. The existing metrics expose backlog and processing duration, but not
an explicit event-age measurement. A timestamp/version signal and a reconciliation
assertion are needed to measure end-to-end freshness. This separates the shorter
HTTP write path from the eventual availability of updated search results.

The published result should include a configuration manifest, dataset seed, workload
script, raw request records, final invariant checks, and an interpretation of the
first saturated resource. Configured alert thresholds may help interpret the run,
but they should not be retroactively presented as a measured service-level objective.

\chapter{Conclusion and Future Work}
\section{Conclusion}
EduFlex delivers a mobile learning experience supported by a secure, transactional,
and observable backend. It covers the path from Material-based Android screens to
REST services, relational storage, caches, messaging, semantic retrieval, integration
tests, containers, and dashboards.

The central achievement is trustworthy learning state. Progress and gamification are
coordinated through transactions, row locks, conditional transitions, and constraints.
Tests demonstrate that concurrent duplicate calls do not duplicate protected rewards.
Caching and asynchronous embedding improve the design without moving authority away
from PostgreSQL.

Observability is part of the implementation: metrics represent infrastructure and
learning operations, dashboards are version-controlled, and availability alerting
has been exercised. CI combines backend correctness, monitoring, and Android delivery.

\section{Future work}
\begin{enumerate}[leftmargin=*]
\item validate complete assessment submissions, define fill-blank progression,
derive reward activity on the server, and align content/review entitlement rules;
\item add a transactional outbox, publisher confirmation, and reconciliation;

payment simulation with verified provider settlement if commercial checkout is required;
